logicc: A Seven-Phase Compiler for Combinational Logic Circuits with Interactive Phase Visualization

Monu Raj
Team CD_2023_Team_1 · Compiler Design Course Project
Source code: https://github.com/monurajj/logic-gate-compiler

Abstract—This paper describes logicc, a compiler for a small hardware-description language that defines combinational logic circuits using the AND, OR, NOT, XOR, NAND, NOR and XNOR gates. The compiler has all six phases of the standard compiler model, which are lexical analysis, syntax analysis, semantic analysis, intermediate code generation, code optimization and target code generation. A shared symbol table and error handler support all of them. A seventh phase runs the generated register-machine assembly on a virtual machine for every input combination and compares each output with a direct evaluation of the source program, so every compiled program is checked for correctness on all of its inputs. A web interface shows the tokens, abstract syntax tree, symbol table, three-address code, optimization log, assembly, truth table and a live gate diagram, and can animate the compilation one step at a time. The optimizer reduces a deliberately redundant 12-gate test program to a single gate. A test suite of 20 tests, including 300 randomly generated programs, passes in full.

Index Terms—compiler design, lexical analysis, recursive-descent parsing, semantic analysis, three-address code, code optimization, register allocation, Boolean logic, combinational circuits.

I. Introduction

Compiler design is usually taught with a general-purpose programming language as the example. A full compiler for such a language is too large for a course project, and its output is hard to check for correctness. This project instead uses Boolean logic circuits as the source language. This choice has three advantages:

  1. The language is small but complete. It has declarations, assignments, nested expressions with operator precedence, and named signals, so every phase has real work to do.
  2. The effect of optimization is visible and measurable. Boolean algebra laws such as a AND 1 = a and a OR NOT a = 1 remove logic gates, and the number of gates can be counted.
  3. Correctness can be checked completely. A circuit with n inputs has only 2n input combinations. The compiled code can be run on all of them and compared with the source program.

The objectives of the project were to implement every phase of the textbook pipeline [1], to report all lexical, syntax and semantic errors in a single run with line and column numbers, to apply several optimization passes and show each change, to generate assembly with register allocation and spilling, to check the generated code automatically, and to show every intermediate state of the compiler in an interactive interface.

II. Source Language

A program declares its inputs and outputs and then assigns a Boolean expression to each signal. Fig. 1 shows a 1-bit full adder written in the language.

The language supports the seven gate keywords and the symbol forms & | ^ ! ~, the constants 0, 1, true and false, and three kinds of comment (#, // and /*…*/). Keywords are case-insensitive. The language also has a short form. If no input is declared, any name that is used but never assigned becomes an input. If no output is declared, every assigned signal becomes an output. This makes the one-line program x = a AND b; valid.

III. Methodology and Architecture

The project follows the AI Product Engineering Track allowed by the course. The compiler was built as a complete application with a generative-AI coding agent (Claude Code [4]), and the author directed and reviewed every step. The work was done one phase at a time, and the Git history records this order: project setup, error handler, Phases 1 to 7, test suite, web interface and deployment. Each phase was specified, implemented, run on the example programs and tested before the next one was started. The implementation is written in Python 3 and uses only the standard library.

Fig. 2 shows the architecture. A driver module (compiler.py) runs the phases in order and stops at the first phase that reports an error. Each phase reports its problems to one shared error handler. The command-line interface (main.py) and the web interface (web.py, plus serverless functions for Vercel deployment) both call the same driver, so they always show the same results.

IV. Phase-by-Phase Design

A. Lexical Analysis

A hand-written scanner reads the source one character at a time. It skips whitespace and comments and produces tokens that record the lexeme, token type, attribute, line and column. Table I lists the token classes. The scanner detects four kinds of lexical error. These are illegal characters such as $, invalid constants such as 2, identifiers that start with a digit such as 3y, and comments that are never closed. The full adder in Fig. 1 produces 40 tokens.

B. Syntax Analysis

A recursive-descent LL(1) parser builds an abstract syntax tree (AST) from the grammar in Fig. 3. Each precedence level has its own rule, which gives the order NOT > AND/NAND > XOR/XNOR > OR/NOR. Left recursion is removed by rewriting rules of the form E → E OR T | T as E → T (OR T)*. The parser handles the repetition with a loop, so binary operators are left-associative. For error recovery the parser uses panic mode. After a syntax error it skips tokens up to the next ; or the start of the next statement, then continues, so one run reports every syntax error in the program.

C. Semantic Analysis and Symbol Table

The semantic analyzer walks the AST and fills the symbol table. Each entry records the name, kind (input, output or wire), type, declaration line, assignment line and number of uses. D. Error Handling

All phases send their diagnostics to one error handler. Each message has a category (Lexical, Syntax or Semantic), a position, and a plain-language explanation. Messages are collected, sorted and printed together. Fig. 4 shows the output for a test file that contains errors on purpose. Because of panic-mode recovery, all six errors are reported in one run.

E. Intermediate Code Generation

A post-order walk of the AST produces three-address code (TAC), with a new temporary for each gate. The same instructions are also shown as quadruples (op, arg1, arg2, result) and as triples, in which a result is referred to by its instruction number. Fig. 5 shows the TAC for the full adder before and after optimization.

F. Code Optimization

The optimizer runs the passes in Table IV repeatedly until a full round makes no change. Every change is logged with the instruction before and after it, and the web interface displays this log. Common-subexpression elimination treats commutative gates as equal, so a AND b and b AND a are computed only once. Dead-code elimination works backwards from the outputs and removes every value that no output depends on.

G. Target Code Generation

The target is LGM (Logic Gate Machine), a register machine designed for this project. It has the instructions LOAD, LOADI, MOV, NOT, the six binary gate operations in three-register form (AND Rd, Ra, Rb), STORE and HALT. Register allocation follows the getReg algorithm in [1]. It keeps a register descriptor that records what each register holds, an address descriptor that records where the current value of each variable is, and next-use information for each instruction. When no register is free, the allocator spills the value whose next use is furthest away. The number of registers can be set on the command line (minimum three). Fig. 6 shows the code for the full adder. The inputs a and b are loaded only once, because the address descriptor shows that they are still in registers.

H. Execution and Verification

The virtual machine runs the generated assembly once for every one of the 2n input combinations, which gives the truth table and the sum-of-minterms form of each output. For each row, the expected output is also computed by evaluating the original AST directly, without phases 4 to 6. If the two results differ, the compiler has a bug, and the differing rows are reported. For the full adder the result is sum = Σm(1, 2, 4, 7) and cout = Σm(3, 5, 6, 7), which are the correct functions [2]. All eight rows match.

V. Interactive Visualization

The web interface (python3 -m logicc.web, which can also be deployed on Vercel) has a code editor on the left. It recompiles as the user types and lists errors, and clicking an error moves the cursor to its line. The right side has one step for each phase:

  • the token table and token stream;
  • a graphical syntax tree, shown with the grammar;
  • the symbol table and the results of the semantic checks;
  • TAC, quadruples and triples;
  • the optimization log, with code before and after;
  • the generated assembly and the verified truth table;
  • a live circuit, in which the optimized netlist is drawn as logic gates. Clicking an input toggles it, and the wires and output lamps update.

A step-by-step mode animates the whole compilation. Tokens appear one at a time, the tree is built level by level, and the optimizations are applied one by one. The animation can be paused, stopped or run at 0.5× to 4× speed. Every technical term in the interface has an information icon with a short explanation. The command-line interface shows the same phases as text tables, and it can stop after any phase (--phase), turn optimization off (-O0), set the number of registers (--regs), and export a Graphviz diagram of the circuit (--dot).

VI. Testing and Results

The test suite has 20 tests in seven groups (Table VI), and all of them pass in about 0.5 s. The most important is a differential fuzz test. It generates 300 random circuits with 1–4 inputs, up to five signals and nested expressions. It compiles each one both with and without optimization, using 3–6 registers, and requires the virtual machine's output to match direct evaluation of the AST for every input combination. This tests the parser, intermediate code generator, optimizer, register allocator and virtual machine together, on programs that were not written by hand. A separate test compiles a four-input circuit with only three registers. It checks that the register allocator spills and that the result is still correct.

The repository includes eight example programs: a simple gate, a half adder, a full adder, a 2-to-1 multiplexer, a 1-bit magnitude comparator, the optimization demo, and one file each for lexical/syntax errors and semantic errors. Each example compiles with the expected result, and the two error files are correctly rejected. The compiler is about 1,800 lines of Python. With the web interface, serverless API and tests, the project is about 3,000 lines.

VIII. Future Scope

  • Sequential logic: flip-flops, registers and a clock, which would need a new kind of semantic check for timing loops.
  • Modules and multi-bit buses: defining a circuit once and reusing it, and signals such as a[3:0], for example to build a 4-bit adder from full adders.
  • Global minimization: adding the Quine–McCluskey method [3] or Karnaugh-map minimization to find minimal circuits. The current rule-based passes only make local improvements.
  • Multi-target code generation: generating Verilog for FPGA synthesis and C for software simulation, in addition to LGM assembly.
  • Faster verification for large circuits: exhaustive checking grows as 2n, so the web interface limits truth tables to 12 inputs. Equivalence checking with binary decision diagrams or a SAT solver would remove this limit.

IX. Conclusion

logicc takes a logic-circuit description through every phase of the standard compiler pipeline, with a shared symbol table and error handler, and adds a verification phase. Because the source language is Boolean logic, the compiler can check every compiled program against its source on all inputs. A fuzz test applies the same check to 300 random programs. The error handler reports all lexical, syntax and semantic errors in one run. The optimizer reduces circuits by a measurable amount (12 gates to 1 in the demonstration). The interactive interface shows each intermediate state, which makes the project useful both as a working compiler and as a tool for teaching how compilers work.
